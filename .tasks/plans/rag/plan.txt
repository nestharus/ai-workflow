Purpose

Provide a high‑recall, modality‑agnostic evidence substrate that:





stores all evidence,



builds a revisable latent structure over it,



compiles bounded, structured context bundles and candidate sets for an external LLM to adjudicate (bugs, contradictions, drift, risks, missing coverage, reorg/optimization suggestions).

This supports reasoning by making large corpora navigable and auditable.

Non-goals





Replacing an LLM or embedding model.



Guaranteeing correctness of conclusions (the LLM/human does adjudication).



Enforcing a fixed ontology or schema as a prerequisite.



Real-time per-document global reclustering on every ingest event.



1) Core invariants

I1. No evidence loss by structure





Every evidence item iii remains addressable and retrievable regardless of clustering outcome.



“Noise,” “unassigned,” or “frontier” are states.

I2. Rebuildable by design

All derived structure is recomputable from:





evidence store,



embeddings (by embedding version),



deterministic seeds/config.

I3. High-recall-first





The system must prefer surfacing uncertainty over silently dropping data.



Any algorithm that yields “noise” must be configured so noise is retained as frontier (queryable) and included in candidate mining.

I4. Local computation

Query-time operations must be bounded to a local neighborhood:





local invariant subgraph,



limited evidence budget,



limited compute steps.

I5. Versioned semantics

Any result presented to an LLM must be reproducible by referencing:





embedding version,



structure snapshot id,



query compilation config,



candidate generation config.

3) Mathematical foundations

3.1 Sparse memberships

Each evidence item i has an embedding vector x_i. Each invariant k has a prototype vector mu_k (or a medoid reference that points to a representative evidence item).





Similarity
Compute a similarity score s(i,k) between x_i and mu_k. Use cosine similarity (recommended) or dot product with unit-normalized vectors.



Top-s selection
For each evidence item i, select the s invariants with the highest similarity scores. Call this set S_i.



Membership weights
Assign weights m(i,k) only for k in S_i. A simple default is “softmax over the top-s similarities”:





Convert similarity scores into positive weights using exp(score / temperature)



Normalize so the weights over S_i sum to 1



All other invariants get weight 0

Temperature is a single global constant that controls how “sharp” the membership distribution is. Lower temperature makes one invariant dominate; higher temperature spreads weight across multiple invariants.





Uncertainty / boundary score (entropy)
Compute an uncertainty score H_i over the non-zero memberships for i:





H_i is high when the evidence item is split across multiple invariants



H_i is low when the evidence item clearly belongs to one invariant

High H_i is a first-class signal that the item sits on a boundary, mixes concerns, or may indicate contradictions or missing structure.



3.2 Induced invariant graph

Build a graph whose nodes are invariants.

Define coupling weight between invariants k and l:





For each evidence item i, if it has membership in both k and l, it contributes mass to the edge (k,l).



Sum these contributions over all evidence items, optionally weighted by amplitude a_i.

Intuition:





If many evidence items belong to both invariants, those invariants are tightly coupled.



This graph is the primary structure used for multi-hop expansion and navigation.



3.3 Optional spectral modes

Once you have an invariant graph (with coupling weights), you can compute “global modes” of that graph using standard spectral graph methods (eigenvectors of a Laplacian or normalized adjacency).

Purpose:





Provide stable global coordinates for navigation and coarse partitioning.



Enable “whole-graph” structure discovery beyond local neighborhoods.

Note:





This is optional. It should never be required for correctness.



It is most useful when K (number of invariants) is large enough that local expansion alone becomes insufficient.



3.4 Diffusion/readout

Query expansion can be implemented as diffusion on the invariant graph:





Seed distribution
Start with a distribution over invariants based on similarity between the query embedding and invariant prototypes.



Spread relevance
Propagate that relevance across the invariant graph by weighted random walk / diffusion. This favors invariants that are strongly connected to the seed set.



Locality control
Stop after a bounded number of steps or keep only the top-N invariants by resulting score. This ensures query-time operations remain local and cost-bounded.

This is a retrieval and prioritization operator over stored structure.



3.5 Diversity

When selecting evidence items to send to an LLM, you need to avoid redundancy.

Two standard approaches:





MMR (Maximum Marginal Relevance): iteratively select items that are relevant to the query while being different from already-selected items.



DPP (Determinantal Point Processes): select a set that is both high-quality and diverse according to pairwise similarity.

Both reduce “wasted context tokens” spent on near-duplicates, which is critical at large-corpus scale.



3.6 Hubness

High-dimensional embedding spaces can exhibit “hubness”: some generic points become nearest neighbors of many other points.

Implications:





Naïve centroid-based clustering can form “super-clusters” around generic hubs.



Nearest-neighbor retrieval can over-return generic items.

Mitigations in this system:





Prefer cosine geometry and unit-normalized vectors.



Prefer medoid prototypes (use a real evidence item as the representative) instead of pure mean centroids.



Track hubness indicators (e.g., invariants with abnormally high degree / mass / entropy).



Treat hub-like invariants as background routing nodes (do not use them as semantic anchors), and split or down-weight them automatically.



4) Algorithms and processes

4.1 Ingestion pipeline

Step 0 - chunking





Text: spans by section/paragraph.



Code: function/class blocks + metadata (path, symbol, commit).



Audio/video: segment into windows/shots; attach transcript if available.



Images: regions or whole-image; attach OCR/captions if available.

Invariant: chunking must be reversible and versioned (payload_ref can point to raw + segment spec).

Step 1 - embedding

Compute x_i​ using an embedding model (external). Store under embedding_version_id.

Step 2 - initial membership assignment

Even before invariants exist, you can:





store embeddings,



support vector retrieval,



compile small context bundles (bootstrap mode).

Step 3 - structure snapshots

Build invariants and memberships into a snapshot_id using one of the nucleation operators below.



4.2 Nucleation - pluggable operators

Operator family A: density-based

HDBSCAN provides hierarchical density-based clustering and can label outliers/noise. Springer Link+1
Rule: noise is retained as FrontierSet.





Output:





stable clusters → invariants



noise points → frontier evidence (still queryable)

Operator family B: centroid-based

Mini-batch k-means is fast and scalable, but can be susceptible to hubness and “super-clusters” if used naïvely.

Safe defaults:





Spherical k-means (unit-normalize vectors; cosine geometry)



Medoid prototypes (prototype references an actual evidence node) to avoid generic/hub centroids.



Balanced/regularized assignment constraints (soft) to prevent a single invariant from absorbing everything.

Operator family C: graph-seeded

Seed invariants from a sparse kNN graph (built by ANN), then refine.

ANN indexes like HNSW support efficient kNN graph construction at scale. arXiv+1
FAISS provides clustering + similarity search implementations (CPU/GPU). GitHub+1



4.3 Frontier and uncertainty handling 

FrontierSet definition

Evidence is in FrontierSet if:





it is labeled noise by a density method, or



max similarity to any invariant is below threshold, or



membership entropy HiH_iHi​ is above threshold.

FrontierSet is first-class





stored,



queryable,



used for candidate generation (often high-yield for contradictions/risks).

Frontier routing

At query time, include a controlled quota of frontier evidence using:





relevance to query,



diversity (MMR/DPP),



boundary score.



4.4 Hubness mitigation

4.4 Hubness mitigation

Hubness is treated as a known geometric pathology.



4.4.1 What hubness is

In high-dimensional embedding spaces, some vectors become “popular”:





they appear unusually often as nearest neighbors,



they are close to many unrelated points,



they represent generic language or boilerplate rather than specific meaning.

If unchecked, hubness causes:





overly large invariants,



semantic collapse (“everything belongs here”),



misleading structure that hides true boundaries.

This risk exists for:





k-means,



nearest-neighbor graphs,



centroid-based routing,



any similarity-driven system.



4.4.2 Design principle

Centroids and invariants are routing constructs under continuous audit.

Therefore:





hubness must be detectable,



hubness must be isolatable,



hubness must never silently dominate navigation.



4.4.3 Hubness signals

The system computes hubness indicators as derived statistics.

An invariant is flagged as hub-like when multiple of the following are true:





Excessive mass





It contains a disproportionate share of total evidence weight.



High average entropy





Many members have spread-out memberships rather than strong attachment.



Abnormally high degree





It connects to many other invariants in the invariant graph.



Low compactness





Members are far from the prototype relative to other invariants.



Generic exemplar content





Medoid or exemplars resemble boilerplate or domain-agnostic text.

These metrics are comparative and percentile-based within a snapshot.
No absolute thresholds are required.



4.4.4 Structural response

When an invariant is flagged as hub-like, the system applies structural corrections.

1) BackgroundInvariant classification

The invariant is marked as a BackgroundInvariant.

Effects:





It is excluded from being a primary semantic anchor.



It remains usable as a routing connector.



It is never removed.

This mirrors stop-word handling in IR, but at the invariant level.



2) Split-within refinement

If a hub-like invariant exceeds stability limits:





Run a secondary nucleation pass only on its member evidence.



Use a density-based or graph-seeded operator.



Produce multiple child invariants with tighter scope.

Key properties:





Local only.



Deterministic given snapshot.



Evidence remains addressable throughout.



3) Medoid preference over centroids

Where possible:





Invariants use medoids (real evidence items) as prototypes instead of mean vectors.

Benefits:





Prevents abstract “average of everything” representatives.



Anchors invariants to concrete content.



Reduces attraction to generic language hubs.



4) Hubness penalty in membership scoring

During membership assignment:





Similarity scores to hub-like invariants are down-weighted.



Evidence is encouraged to attach to more specific alternatives.

This is a structural bias:





the penalty derives from hubness indicators,



it adapts automatically as structure evolves.



4.4.5 Frontier interaction

Hubness mitigation never discards evidence.

Instead:





Evidence that does not cleanly reattach after hub correction



naturally falls into the FrontierSet

Frontier evidence:





remains queryable,



is prioritized for candidate mining,



often contains contradictions, risks, or missing structure.

This directly prevents the “data thrown away” failure mode.



4.4.6 Why this does not require tuning

No manual tuning is required because:





Signals are relative (percentiles, comparisons within snapshot).



Corrections are structural (split, classify, down-weight).



The system does not aim for a “perfect clustering.”



High entropy and ambiguity are acceptable, visible states.

Hubness becomes observable and manageable.



4.4.7 Failure modes explicitly prevented

This section guarantees prevention of:





Super-clusters absorbing unrelated content



Generic boilerplate dominating navigation



Silent loss of recall due to over-general invariants



Hard dependence on centroid correctness



One-shot clustering errors becoming permanent



4.5.1 Inputs and guarantees

Inputs





query_payload
The user query (text or multimodal reference).



query_embedding
Embedding of the query using a specific embedding version.



embedding_version_id
Must match the structure snapshot.



snapshot_id
Identifies the invariant structure in use.

Token or evidence-count budget for the bundle.

Access control, safety, and compliance filters.

Guarantees

4.5.2 Seed invariant selection





Similarity lookup
Compute similarity between the query embedding and invariant prototypes.



Top-k invariant selection
Select the top-k invariants most similar to the query.
This is the initial “semantic footprint” of the query.



Stability check
If the selected invariants are flagged as hub-like or background-only:





expand selection to nearby non-hub invariants, or



include frontier evidence early to avoid generic collapse.



4.5.3 Local structural expansion

From the seed invariants, expand locally using the invariant graph.

Allowed expansion mechanisms:





weighted neighbor expansion by coupling strength



bounded random walk or diffusion



personalized PageRank seeded on the query distribution

Constraints:





expansion depth and breadth are capped



only invariants within the local subgraph are considered



no global traversal is allowed

Purpose:





capture multi-hop relevance



surface implicit relationships



preserve locality and performance



4.5.4 Evidence selection per invariant

For each selected invariant:





Candidate pool





evidence with non-zero membership in the invariant



optionally include nearby frontier evidence





Scoring dimensions
Each evidence item is scored by:





relevance to the query



representativeness within the invariant



membership confidence



novelty relative to already-selected evidence



anomaly/boundary indicators (entropy, drift flags)





Selection
Select a bounded number of evidence items per invariant.

No invariant is allowed to monopolize the bundle.



4.5.5 Diversity and redundancy control

To prevent redundant context:





Apply diversity-aware selection:





Maximum Marginal Relevance (MMR), or



Determinantal Point Processes (DPP), or



equivalent diversity constraints

Effects:





near-duplicate passages are suppressed



multiple perspectives are preserved



token budget is used efficiently

This step is mandatory for large corpora.



4.5.6 Frontier inclusion

A fixed quota of the bundle is reserved for FrontierSet evidence:





high-entropy items



boundary-crossing items



items weakly attached to any invariant

Purpose:





prevent silent omission of ambiguous or messy regions



surface likely contradiction, risk, or missing-spec candidates



preserve high recall

Frontier inclusion is controlled.



4.5.7 Candidate issue extraction

Examples:

invariants with unresolved entropy

These are prompts for LLM or human interpretation.

4.5.9 Determinism and auditability





All selection steps are deterministic or seeded.

4.5.10 Failure modes explicitly avoided

This design prevents:

4.6 Candidate generation

This section defines how the system generates high-recall candidate sets for review by an LLM or human. Candidate generation is structural. It identifies where attention is warranted.

All candidates are derived from the same underlying structure (evidence, memberships, invariant graph, statistics). No task-specific rules or schemas are embedded.



4.6.1 Design principles





High recall over precision
Candidates may include false positives; missing true issues is the primary failure.



No semantic assumptions
The system does not encode what a “bug,” “risk,” or “contradiction” is.



Structure-only signals
All candidates are produced from geometry, overlap, density, change, and topology.



Bounded output
Candidate lists are capped and ranked to remain reviewable.



4.6.2 Candidate types

Each candidate type is a view over the same data. None are mandatory, and none alter structure.



A) Boundary evidence candidates

What they are
Evidence items that sit between multiple invariants or weakly belong anywhere.

Structural signals





High membership entropy



Comparable membership weights across multiple invariants



Contribution to multiple invariant edges

Why they matter
Boundary evidence is where:





contradictions hide



responsibilities blur



missing abstractions appear



bugs and risks often originate

These are prime LLM adjudication targets.



B) Unresolved invariant candidates

What they are
Invariants that never stabilize into a tight structure.

Structural signals





High average membership entropy



Low compactness



Large, heterogeneous membership sets



Frequent internal reassignments across snapshots

Why they matter
Unresolved invariants often indicate:





ambiguous intent



missing specifications



overly broad responsibilities



documentation gaps



C) Rewiring and topology-change candidates

What they are
Structural relationships that change significantly over time.

Structural signals





Large increases or decreases in coupling weight between invariants



New invariant edges appearing



Previously strong edges weakening or disappearing

Why they matter
Topology changes reflect:





architectural drift



new dependencies



responsibility leakage



refactors with unintended consequences



D) Coverage gap candidates

What they are
Regions that appear relevant but under-supported.

Structural signals





Invariants highly relevant to a query but with low evidence mass



Expected neighbors present elsewhere but missing locally



Sudden mass loss relative to a baseline snapshot

Why they matter
These often correspond to:





missing tests



undocumented behavior



incomplete migrations



unimplemented requirements



E) Drift-from-intent candidates

What they are
Differences between a reference state (intent) and a current state.

Structural signals





Additions: new invariants or mass appearing



Removals: invariant mass disappearing



Shifts: changes in membership distribution or compactness



Rewiring: changes in invariant connectivity

Why they matter
They provide a complete, structure-level diff without relying on text comparison.



F) Frontier candidates

What they are
Evidence not cleanly captured by any invariant.

Structural signals





No memberships



Very low similarity to all invariants



Persistent frontier status across snapshots

Why they matter
Frontier evidence often represents:





novel ideas



edge cases



anomalies



early signals of change

Frontier is explicitly retained and surfaced.



4.6.3 Candidate ranking and bounding

Candidates are ranked using structural severity scores, such as:





degree of boundary overlap



magnitude of change from baseline



rarity within the corpus



persistence across snapshots

Ranking is comparative within a snapshot; no absolute thresholds are required.

Each candidate type has a configurable cap to ensure:





bounded review workload



predictable query-time cost



4.6.4 Candidate output format

Candidates are emitted as a structured list containing:





candidate type



severity score



evidence_id(s) and/or invariant_id(s)



short structural explanation (machine-generated)



snapshot_id and embedding_version_id

No natural-language judgment is included at this stage.



4.6.5 Interaction with the LLM

The LLM’s role is:





to interpret candidates,



to adjudicate meaning,



to explain implications,



to suggest actions.

The system never:





suppresses candidates based on LLM output,



rewrites structure directly from LLM responses,



assumes LLM judgments are correct.

LLM outputs may be stored as annotations for future reference.



4.6.6 Determinism and auditability





Candidate generation is deterministic per snapshot and configuration.



Each candidate can be traced back to:





the evidence involved,



the invariants involved,



the statistics that triggered it.



This enables reproducible audits and post-mortems.



4.6.7 Failure modes explicitly avoided

This design prevents:





hiding anomalies inside clusters



requiring task-specific heuristics



missing issues due to narrow retrieval



silent bias toward “clean” data



overfitting candidate logic to one domain



4.7 Drift handling

This section defines how the system detects and represents drift without assuming semantics, correctness, or task-specific rules. Drift is treated as structural change in the evidence substrate and is decomposed in a way that is complete, auditable, and interpretable by an LLM or human.



4.7.1 What “drift” means in this system

Drift is any change in structure between two snapshots.

A snapshot captures:





evidence



embeddings (by version)



invariants



memberships



invariant graph



statistics

Drift is detected by comparing two snapshots.

Importantly:





Drift is not inherently good or bad.



Drift does not imply error.



Drift is simply “something changed.”

Interpretation is deferred.



4.7.2 Drift categories

All drift falls into four non-overlapping categories. This guarantees nothing structural is missed.



A) Additions

Definition
New structure that exists in the later snapshot but not the reference snapshot.

Structural signals





New invariants



New evidence mass assigned to previously empty regions



New invariant edges (new couplings)

Interpretation examples





New features



New requirements



New topics or responsibilities



New risks introduced



B) Removals

Definition
Structure present in the reference snapshot that is absent or significantly reduced in the later snapshot.

Structural signals





Invariants whose total mass drops sharply



Evidence moving to frontier or becoming unassigned



Invariant edges weakening or disappearing

Interpretation examples





Deprecated functionality



Removed concepts



Missing documentation or tests



Accidental loss during refactor



C) Shifts

Definition
Structure that persists but behaves differently.

Structural signals





Membership redistribution within an invariant



Increased or decreased entropy



Compactness changes



Changes in the composition of exemplar evidence

Interpretation examples





Semantic drift



Scope creep or contraction



Reinterpretation of intent



Gradual erosion of clarity



D) Rewiring

Definition
Changes in how invariants relate to each other.

Structural signals





Large changes in coupling strength between invariant pairs



New bridges forming between previously distant regions



Old bridges weakening or breaking

Interpretation examples





Architectural drift



New dependencies



Responsibility leakage



Tightening or loosening of system boundaries



4.7.3 Intent drift

Intent is represented as a reference snapshot.

To detect drift from intent:





Select a baseline snapshot that encodes the intended state.



Compare the current snapshot against it using the four categories above.

This yields a complete structural diff:





what was added relative to intent



what was removed



what shifted



what rewired

No text diffing is required.



4.7.4 World drift

World drift refers to:





new documents



updated documents



changes in emphasis over time

Handled by:





periodic snapshot builds



time-series tracking of invariant mass, entropy, and coupling



optional change-point detection on those metrics

World drift answers:
“Is the corpus evolving, and where?”



4.7.5 Model drift

Changing the embedding model changes geometry.

Protocol





Version embeddings
Each embedding model has a unique embedding_version_id.



Re-embed evidence
Evidence is re-embedded asynchronously.



Build new structure
New invariants and memberships are built under the new embedding version.



Crosswalk invariants
Map old invariants to new invariants by overlap in shared evidence membership.
This produces a best-effort correspondence.



Dual-read period
Queries may reference either version explicitly during migration.



Migration drift report
Differences attributable to the model change are reported separately from content changes.

This avoids silent corruption and enables auditability.



4.7.6 Drift severity and prioritization

Drift is ranked using structural magnitude:





size of mass change



entropy change



persistence across snapshots



number of affected invariants or edges

Severity is comparative within a snapshot range.



4.7.7 Drift as candidate generation

Drift events automatically generate candidates:





“This region changed significantly”



“This relationship appeared or disappeared”



“This area lost clarity”

They are fed into the candidate generation pipeline and reviewed by:





LLMs



humans



automated policies (optional)

The system never labels drift as “bad” or “good.”



4.7.8 Failure modes explicitly avoided

This design prevents:





silent semantic shifts



hidden regressions after refactors



undetected scope creep



embedding model upgrades corrupting meaning



reliance on brittle text diffs



4.8 Cold start

Modes





Bootstrap mode (N < N_min)





store embeddings

optional ephemeral clustering over top retrieved results per query



Activation mode (N ≥ N_min)

Steady state

8) Risk register

Addressed risks from critique

Risks

R1. Adversarial/poisoned content





Mitigation: trust weights a_i​, source-based gating, anomaly signals, quarantine sources, content scanning.

R2. Privacy leakage via embeddings





Mitigation: ACL-aware retrieval, per-tenant indexes or encrypted enclaves depending on policy; audit logs; redaction policies.

R3. Feedback-loop collapse (LLM rewriting structure)





Mitigation: LLM outputs are annotations/suggestions only; structural changes require deterministic rules + gated approval.

R4. Non-determinism and irreproducibility





Mitigation: snapshot/version IDs, seeded sampling, immutable bundle manifests.

R5. Cost blowups





Mitigation: strict locality; sparse memberships; bounded bundle budgets; incremental rebuild strategies; GPU acceleration where appropriate (FAISS GPU for large scale). arXiv

R6. Semantic brittleness from embedding quality





Mitigation: multiple embedding versions, evaluation harness, “model drift” reports, and fallback retrieval modes.
