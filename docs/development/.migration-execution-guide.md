## Migration Execution Guide: Mixed Content Breakdown (TICKET-6)

This guide describes how to execute the mixed-content documentation breakdown using the information migration workflow for all files listed in `docs/development/.content-breakdown-plan.md`.

### 1. Prerequisites

- Review `docs/development/.content-breakdown-plan.md` and confirm the list of mixed-content candidate files and their target GENERAL/PROJECT locations.
- Read `docs/processes/information-migration.yml` to understand the migration workflow, comparison CSV schema, and DuckDB queries.
- Verify the `.knowledge/` directory structure exists (including `originals/`, `comparisons/`, and any migration tracking subdirectories).
- Ensure `uv` and the migration commands (`start-migration`, `compare-yml-docs`, `query-comparisons`, `mark-resolved`, `validate-migration`) are available in the environment.
- Ensure automation scripts are available: `create-breakdown`, `rebuild-from-breakdown`, `batch-mark-resolved`, `track-additions`, `validate-addition`, `generate-migration-report`, `record-movement`.

### 2. Migration Workflow Template (Per File)

For each mixed-content file listed in the breakdown plan, perform the following steps, substituting module/pattern names and paths as needed.

```bash
# Step 1: Start migration for mixed-content file
uv run start-migration --original-file docs/development/project/<module>/project.<module>.<pattern>.yml
# Output: Task ID and timestamped original path

# Step 2: Create GENERAL version (manual work)
# - Copy protocol/framework patterns to docs/development/general/<module>/general.<module>.<pattern>.yml
# - Remove all app/* references
# - Update doc_id to general-<module>-<pattern>
# - Update primary_runtime_references to be empty or generic

# Step 3: Update PROJECT version (manual work)
# - Keep only app/* implementation details
# - Remove general protocol/framework patterns
# - Ensure doc_id remains project-<module>-<pattern>
# - Keep primary_runtime_references pointing to app/* files

# Step 4: Run comparison
uv run compare-yml-docs --path docs/development
# Output: Comparison CSV in .knowledge/comparisons/<pattern>.csv

# Step 5: Query unresolved differences
uv run query-comparisons --pattern <pattern> --exclude-resolved
# Output: List of IDs not found in either GENERAL or PROJECT file

# Step 6: Resolve intentional differences (if any)
uv run mark-resolved --id <element_id> --source-file <original> --split-file <target>
# Repeat for each intentional difference (e.g., rewording, restructuring)

# Step 6b: Record information movements (optional, for detailed tracking)
uv run record-movement \
  --id <element_id> \
  --source-file <original> \
  --target-file <target> \
  --reason "Moved to language-specific file" \
  --coverage "Implementation details" \
  --before-text "Original sentence..." \
  --after-text-source "See target file..." \
  --target-before "Target sentence before..." \
  --target-after "Target sentence after..."
# Output: New record in .knowledge/movements/movements.csv

# Step 7: Track additions (new IDs in target files)
uv run track-additions --pattern <pattern>
# Output: New records in .knowledge/additions/additions.csv

# Step 8: Validate additions
uv run validate-addition --id <addition_id> --validated --in-scope --meaningful
# Output: Updated flags in additions.csv

# Step 9: Generate review report for non-identical items
uv run generate-migration-report --pattern <pattern>
# Output: YML report in .knowledge/reports/<pattern>-review.yml

# Step 10: Validate migration
uv run validate-migration --task-id <uuid>
# Output: Validation status (completed or failed with unresolved count)
```

### 4. Common Patterns to Watch For

- GENERAL content:
  - HTTP methods, status codes, URL conventions, pagination, versioning strategies.
  - FastAPI router patterns, dependency usage, middleware ordering, settings patterns.
  - Python architectural, repository, service, and factory patterns.
  - SurrealDB and Elasticsearch connection/repository patterns that are not tied to project file paths.
- PROJECT content:
  - References to `app/core/factory.py`, `app/core/config.py`, `app/core/settings.py`, `app/core/errors.py`, `app/core/exceptions.py`, `app/core/middleware.py`.
  - References to `app/contracts/`, `app/contracts/errors.py`.
  - References to `app/api/`, `app/api/v1/router.py`, `app/api/v1/dependencies.py`.
  - References to `app/services/`, `app/repositories/`, `app/infrastructure/`.
  - Explicit mentions of `create_app` or other project-specific functions/classes.
- Intentional differences:
  - Rewording for clarity without changing meaning.
  - Restructuring sections (e.g., grouping related patterns) while preserving content.

### 5. Validation Criteria

For each migration task, treat the migration as complete only when:

- All IDs from the original PROJECT file appear in at least one of the split files (GENERAL or PROJECT).
- Every GENERAL file is free of `app/*` references and project-specific function/class names.
- Every PROJECT file retains all app-specific guidance and paths identified in `.content-breakdown-plan.md`.
- All intentional rewordings or structural changes are recorded via `uv run mark-resolved`.
- `uv run validate-migration --task-id <uuid>` reports 0 unresolved differences for that task.

### 6. Granular ID Breakdown Process

For complex migrations with mixed content, use this granular ID-by-ID approach:

#### Step 1: Create Breakdown Table

Create a `.id-breakdown.md` file (e.g., `docs/development/rest.id-breakdown.md`) from the timestamped original:

```markdown
| ID | Original Text Summary | Classification | Rationale | Target |
|----|----------------------|----------------|-----------|--------|
| url.prefix | Mount /api/{version} using create_app... | MIXED→split | Rule=GENERAL; app ref=PROJECT | Both |
| url.resource-naming | Use plural kebab-case... | GENERAL | Pure URL convention | GENERAL |
```

Classifications:
- **GENERAL**: Pure protocol/principle rules (no lang/framework/app)
- **PROJECT**: Concrete wiring with app/* paths, framework specifics
- **MIXED→split**: Contains both; split into GENERAL rule + PROJECT wiring
- **PARK**: Belongs in another module (e.g., Pydantic→general.python)

#### Step 2: Empty and Rebuild Files

Per the breakdown table:
1. Empty GENERAL file, retain metadata, populate ONLY GENERAL-classified items
2. Empty PROJECT file, retain metadata, populate ONLY PROJECT-classified items
3. For MIXED→split items, create appropriate variants in both files

#### Step 3: Run Comparison and Mark Resolutions

```bash
# Regenerate comparisons
uv run compare-yml-docs --path docs/development

# Query unresolved differences
uv run query-comparisons --pattern rest.api-patterns --exclude-resolved

# Mark each MIXED→split item as resolved (example)
uv run mark-resolved \
  --id url.prefix \
  --source-file .knowledge/originals/20251201T134735Z-project.rest.api-patterns.yml \
  --split-file docs/development/general/rest/general.rest.api-patterns.yml \
  --split-file docs/development/project/rest/project.rest.api-patterns.yml
```

#### Step 4: Validate

```bash
uv run validate-migration --task-id <uuid>
# Expected: 0 unresolved differences
```

#### Script Template for Classification

```python
import yaml

with open('original.yml') as f:
    doc = yaml.safe_load(f)

for section in doc.get('sections', []):
    for item in section.get('items', []):
        text = item.get('text', '')
        item_id = item.get('id', '')
        # Classify based on content
        has_app_ref = 'app/' in text or 'create_app' in text
        has_framework = 'FastAPI' in text or 'Pydantic' in text or 'fastapi.' in text
        if has_app_ref or has_framework:
            classification = 'PROJECT' if not has_app_ref else 'MIXED→split'
        else:
            classification = 'GENERAL'
        print(f"| {item_id} | {text[:50]}... | {classification} |")
```

### Automation Scripts for Granular Breakdown

Three automation scripts streamline the granular ID breakdown process:

#### 1. Create Breakdown Table

Generate a classification table from a timestamped original:

```bash
uv run create-breakdown \
  --original-file .knowledge/originals/20251201T134735Z-api-patterns.yml \
  --output docs/development/rest.id-breakdown.md \
  --auto-classify
```

- `--auto-classify`: Apply rule-based classification (GENERAL/PROJECT/MIXED→split/PARK)
- Output: Markdown table with ID, text summary, classification, rationale, target

#### 2. Rebuild Files from Breakdown

Rebuild GENERAL and PROJECT files based on the breakdown table:

```bash
uv run rebuild-from-breakdown \
  --breakdown-table docs/development/rest.id-breakdown.md \
  --original-file .knowledge/originals/20251201T134735Z-api-patterns.yml \
  --general-output docs/development/general/rest/general.rest.api-patterns.yml \
  --project-output docs/development/project/rest/project.rest.api-patterns.yml \
  --variants-file docs/development/rest.text-variants.yml  # optional
```

- `--variants-file`: Optional YAML file with explicit GENERAL/PROJECT text variants for MIXED→split items
- For MIXED→split items without explicit variants, applies regex-based stripping for GENERAL text

#### 3. Batch Mark Resolved

Batch-mark all MIXED→split items as resolved:

```bash
uv run batch-mark-resolved \
  --breakdown-table docs/development/rest.id-breakdown.md \
  --original-file .knowledge/originals/20251201T134735Z-api-patterns.yml \
  --general-file docs/development/general/rest/general.rest.api-patterns.yml \
  --project-file docs/development/project/rest/project.rest.api-patterns.yml
```

- Invokes `mark-resolved` via subprocess for each MIXED→split item
- Supports multiple `--split-file` arguments (GENERAL and PROJECT)
- Reports success/failure count with detailed error messages

### 7. Troubleshooting

- If `validate-migration` fails:
  - Re-run `uv run query-comparisons --pattern <pattern> --exclude-resolved` to list unresolved differences.
  - Check whether the missing IDs were accidentally omitted from both GENERAL and PROJECT files.
  - If content was intentionally dropped or reworded, add `mark-resolved` entries pointing from the original to the appropriate split file.
- After fixing issues:
  - Re-run `uv run compare-yml-docs --path docs/development` to regenerate comparisons.
  - Re-run `uv run validate-migration --task-id <uuid>` until the status is `completed` and unresolved differences count is 0.
- Keep `.migration-status.md` updated after each major step (start-migration, comparison, validate-migration) so the overall progress stays accurate.
- **For post-validation refinements** (e.g., stricter GENERAL/PROJECT separation):
  - No new `start-migration` needed; use the existing task ID and timestamped original.
  - Re-run `uv run compare-yml-docs --path docs/development` to regenerate comparisons after refinement edits.
  - Run `uv run query-comparisons --pattern <pattern> --exclude-resolved` to identify differences from rephrasing.
  - Use `uv run mark-resolved --id <id> --source-file <timestamped-original> --split-file <general-or-project>` for each intentionally rephrased or moved item.
  - Run `uv run validate-migration --task-id <uuid>` to confirm 0 unresolved differences.
  - Update `.migration-status.md` with refinement notes and new validation timestamp.
- If `track-additions` reports warnings about failed CSV queries:
  - Check that comparison CSVs are valid and not corrupted.
  - Regenerate comparisons using `uv run compare-yml-docs --path docs/development`.
- If `generate-migration-report` produces empty reports:
  - Verify that unresolved differences exist and are not all identical matches.
  - Check that items have not all been marked as resolved.
  - Ensure origin_type is 'original' for the items you expect in reports.
- If `batch-mark-resolved` fails for specific IDs:
  - Run `uv run mark-resolved` manually with verbose output to diagnose the issue.
  - Check that the element ID exists in both the original file and the split files.
  - Verify file paths are correct and files are readable.
