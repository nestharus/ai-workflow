## Content Breakdown Plan: Mixed PROJECT Documentation

### Overview

This plan identifies documentation files in `docs/development/project/` that contain **mixed content** (GENERAL protocol/framework patterns plus PROJECT-specific `app/*` references) and describes how each will be split into separate GENERAL and PROJECT documents using the information migration workflow in `docs/processes/information-migration.yml`.

The moved PROJECT files are treated as the **originals** for migration. For every mixed-content file we will:
- Start a tracked migration task
- Create a new GENERAL file under `docs/development/general/<module>/`
- Update the existing PROJECT file under `docs/development/project/<module>/` to keep only project-specific implementation details
- Validate via comparison that no content is lost and all differences are resolved

### Automation Scripts

Three automation scripts streamline the granular ID breakdown process:
- `uv run create-breakdown`: Generate classification tables from timestamped originals
- `uv run rebuild-from-breakdown`: Rebuild GENERAL/PROJECT files from breakdown tables
- `uv run batch-mark-resolved`: Batch-mark MIXED→split items as resolved

See `docs/development/.migration-execution-guide.md` for detailed usage examples.

### Global Validation Criteria

Across all mixed-content migrations, the migration is considered **complete** when:

- Every documentation element (e.g., `id`/anchor) from each original PROJECT file appears in either its GENERAL or PROJECT split file.
- **GENERAL files are protocol-only**: No language-specific constructs (Pydantic, ORM), no framework-specific APIs (FastAPI decorators, status constants), no `app/*` references. For REST, this means pure HTTP/URL/header rules.
- **PROJECT files are wiring-only**: All language/framework specifics (Pydantic models, FastAPI handlers, `app/*` paths) belong here. No descriptive protocol rules that could stand alone.
- All intentional rewordings or restructurings are marked as resolved using `uv run mark-resolved`.
- `uv run validate-migration --task-id <uuid>` reports 0 unresolved differences for every TICKET-6 migration, using the UUID task_id values from `.knowledge/migrations/tasks.csv` and `docs/development/.migration-status.md`.

### Automation Script Validation

When using automation scripts, additionally verify:
- `create-breakdown` extracted all IDs from the original file (compare total count)
- `rebuild-from-breakdown` preserved all non-PARK items in GENERAL or PROJECT files
- `batch-mark-resolved` successfully marked all MIXED→split items (check success count)
- Generated files pass `compare-yml-docs` and `validate-migration` checks

### Granular Rebuild Process

For complex migrations (like REST), use ID-by-ID breakdown:

1. Create `<module>.id-breakdown.md` table classifying EVERY ID from timestamped original
2. Classifications: GENERAL (protocol-only), PROJECT (wiring-only), MIXED→split (both), PARK (other module)
3. Empty and rebuild files per classification
4. Run `compare-yml-docs` and `query-comparisons`
5. `mark-resolved` for EACH MIXED→split item (specify both --split-file targets)
6. `validate-migration` until 0 unresolved

See `docs/development/rest.id-breakdown.md` as reference implementation.

### Automated Granular Breakdown Workflow

The granular breakdown process can be automated using three scripts:

#### Step 1: Generate Breakdown Table

```bash
uv run create-breakdown \
  --original-file .knowledge/originals/<timestamp>-<pattern>.yml \
  --output docs/development/<pattern>.id-breakdown.md \
  --auto-classify
```

- Parses the timestamped original YAML file
- Extracts all IDs with text content
- Applies rule-based classification (GENERAL/PROJECT/MIXED→split/PARK)
- Generates markdown table with ID, text summary, classification, rationale, target
- `--auto-classify` flag enables automatic classification; omit for manual review

#### Step 2: Review and Adjust Classifications

Manually review the generated breakdown table and adjust classifications as needed:
- Verify GENERAL items contain no framework/app references
- Verify PROJECT items contain concrete wiring with app/* paths
- Verify MIXED→split items require splitting into both files
- Verify PARK items belong in other modules

#### Step 3: Rebuild Files

```bash
uv run rebuild-from-breakdown \
  --breakdown-table docs/development/<pattern>.id-breakdown.md \
  --original-file .knowledge/originals/<timestamp>-<pattern>.yml \
  --general-output docs/development/general/<module>/general.<module>.<pattern>.yml \
  --project-output docs/development/project/<module>/project.<module>.<pattern>.yml
```

- Parses the breakdown table to extract classifications
- Rebuilds GENERAL file with GENERAL and MIXED→split items (protocol-only text)
- Rebuilds PROJECT file with PROJECT and MIXED→split items (implementation text)
- For MIXED→split items, applies regex-based stripping for GENERAL text or uses explicit variants if provided via `--variants-file`

#### Step 4: Batch Mark Resolved

```bash
uv run batch-mark-resolved \
  --breakdown-table docs/development/<pattern>.id-breakdown.md \
  --original-file .knowledge/originals/<timestamp>-<pattern>.yml \
  --general-file docs/development/general/<module>/general.<module>.<pattern>.yml \
  --project-file docs/development/project/<module>/project.<module>.<pattern>.yml
```

- Parses the breakdown table to find MIXED→split items
- Invokes `mark-resolved` for each item with both GENERAL and PROJECT split files
- Reports success/failure count with detailed error messages

#### Step 5: Validate

```bash
uv run validate-migration --task-id <uuid>
```

- Reruns comparison and checks for unresolved differences
- Expected: 0 unresolved differences
